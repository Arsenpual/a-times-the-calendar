# แผนพัฒนา AI Mode จาก mockup เป็นหน้าใช้งานจริง (PC)

## ความคืบหน้า 27 ตุลาคม 2026

- เริ่ม Phase 0: ทำตารางเทียบ mockup กับพฤติกรรมจริงไว้ใน `src/features/activity/assistant/AI-MODE-BEHAVIOR-CONTRACT.md`
- เริ่ม Phase 1: AI Mode มีแชทกับแผงงานด้านขวาบน PC เปิด/ปิดแผงได้ โดยยังใช้ conversation hook และ backend เดิม
- เริ่ม Phase 2 และ 4 เฉพาะส่วนที่พึ่งพาโครงหน้า: แสดงป้ายแหล่งคำตอบ, ยืนยันก่อนเริ่มแชทใหม่, ส่งด้วย Enter, และแสดงขั้นตอนสร้างกิจกรรมในแผงงาน โดยเริ่มถามในแชทก่อนเปิดฟอร์ม
- งานต่อเนื่อง: ย้ายสำเนา Telegram ไปไว้ท้ายแผงงานบน PC, แสดงช่วงวันที่ที่ backend อ่านปฏิทินจริง, เพิ่มปุ่มยกเลิกการสร้าง และคงข้อมูลที่เลือกไว้เมื่อสร้างร่างไม่สำเร็จ
- เพิ่มข้อความสรุปร่างจากข้อมูลที่ backend คืนมา ก่อนให้ผู้ใช้ตรวจและบันทึกในฟอร์ม และป้องกันคำขอร่างที่ตอบช้าจากการเปิดฟอร์มหลังออกจาก AI Mode
- งานต่อเนื่องรอบถัดมา: แก้ชื่อ วัน เวลา และระยะเวลาที่เลือกแล้วได้ในแผงงาน พร้อมข้อมูลล่าสุดในแชท; ตรวจค่าก่อนสร้างร่าง และย้ายข้อผิดพลาดมาไว้ท้ายบทสนทนา
- ทดสอบการส่งร่างไปฟอร์มด้วยบริการจำลองทั้งกรณีล้มเหลวและสำเร็จ; หลังล้มเหลวแก้ข้อมูลและกดสร้างร่างอีกครั้งจากแผงงานได้ โดยซ่อนคำถามปฏิทินที่ไม่เกี่ยวระหว่างขั้นตอน
- ทดสอบเวลาชนเกิน 3 กิจกรรม: ยังไม่เปิดฟอร์มจนผู้ใช้เลือกเวลาใหม่ และแสดงวันที่ของตัวเลือก; ตรวจร่างที่ backend ส่งกลับก่อนเปิดฟอร์ม พร้อมปรับช่วงระยะเวลาให้ตรงกับ backend (30–720 นาที)
- ทดสอบกับ `ActivityModal` จริงใน browser fixture: เปิดร่างไม่บันทึกอัตโนมัติ, แก้ข้อมูลก่อนบันทึก, บันทึกล้มเหลวแล้วลองใหม่, ยกเลิกโดยไม่บันทึก; ทดสอบคำขอร่างที่ตอบช้าหลังออกและกลับเข้า AI Mode แล้วไม่เปิดฟอร์มจากคำขอเก่า
- Phase 5 เพิ่มการกันคำตอบที่มาช้าจากแชทอิสระและแชทวางแผนหลังออกจาก AI Mode หรือเริ่มแชทใหม่; คำขอคำตอบสำเร็จรูป สรุปวันนี้ และร่างกิจกรรมตรวจรุ่นบทสนทนาเดียวกัน รวมทั้งคืนสถานะกำลังรอเมื่อออกจากหน้า
- Phase 3 แสดงคำตอบอ่าน Calendar, หาเวลาว่าง และวางแผนเป็นการ์ดตามชนิดผลจริง; การ์ด Calendar แสดงช่วงวันที่ที่ backend ส่งมา และการ์ดหาเวลาว่างรองรับกรณีไม่พบตัวเลือกโดยไม่สร้างช่วงเวลาขึ้นเอง
- Phase 3 แยกข้อผิดพลาดอ่าน Calendar ชั่วคราวออกจากสิทธิ์หมดอายุด้วยรหัสจาก backend; แชทแสดงสถานะเฉพาะพร้อมปุ่มลองอีกครั้งหรือยืนยันตัวตน โดยไม่แสดงเป็นตารางว่าง
- Phase 5 ทดสอบสลับบัญชีขณะมีคำตอบ AI ค้าง: บทสนทนาแยกตามบัญชี, บัญชีเดิมโหลดประวัติตัวเองกลับมา และคำตอบที่มาหลังสลับไม่ปรากฏในบัญชีใหม่
- Phase 4 ตรวจร่างแผนหลายกิจกรรมหลังแก้ไขชื่อและเวลาในแชท; รายการที่เลือกและผิดเงื่อนไขจะหยุดปุ่มสร้างพร้อมแสดงเหตุข้างรายการ ก่อนส่งให้ขั้นตอนบันทึกเดิม
- Phase 3 หลังรีโหลด ประวัติผลหาเวลาว่างและร่างแผนที่เคยมีตัวเลือกจะแจ้งว่าตัวเลือกเดิมหมดอายุและให้คำนวณใหม่; เก็บเฉพาะข้อความกับจำนวนผลใน localStorage ไม่เก็บร่างหรือปุ่มที่อาจอ้างตารางเก่า
- Phase 4 การบันทึกแผนหลายรายการแยกผลสร้างสำเร็จออกจากปัญหาข้อมูลประกอบและการรีโหลด; แสดงผลสำเร็จบางส่วนพร้อมคำเตือนให้ตรวจ Calendar และไม่เปิดให้ส่งทั้งชุดซ้ำจากการ์ดเดิม
- Phase 6 เชื่อมอากาศกับกิจกรรมบน PC ผ่าน Google Weather และเกณฑ์เลือกช่วงร่วมกับ Telegram; เลือกช่วงแล้วเปิด ActivityModal เพื่อตรวจเอง มีปุ่มถามต่อวันอื่นที่สถานที่เดิม
- ยังต้องทดสอบเครื่องมือกับ Calendar ของบัญชีจริงและสิทธิ์ที่หมดอายุจริงใน Phase 3, เส้นทางตรวจร่างกับ Calendar จริงใน Phase 4, และเส้นทาง Google Weather จริงใน Phase 6

## ขอบเขตและหลักการ

- ใช้ `activity-mode-ai-workspace-mockup.jsx` เป็นแบบของหน้าจอ PC โดยอ้างอิงพฤติกรรมจริงจากหน้า AI Mode และ backend ปัจจุบัน
- พัฒนาทีละ phase ให้แต่ละช่วงเปิดใช้งานและทดสอบได้ ก่อนเริ่มช่วงถัดไป
- ใช้บริการและสิทธิ์เดิมของเว็บ: การคุยอิสระผ่าน `/api/ai/free-conversation`, การวางแผนผ่าน `/api/ai/activity-conversation`, ข้อมูลตารางจากเครื่องมือเดิม และโควต้า AI เดิม ห้ามคัดลอกข้อมูลจำลองหรือ logic จำลองจาก mockup เข้า production
- คงการตรวจร่างและการยืนยันโดยผู้ใช้ก่อนสร้างกิจกรรมทุกครั้ง ไม่ให้ AI เขียนปฏิทินเอง
- ทำ PC ก่อน ทดสอบที่ความกว้าง 1280 และ 1440 พิกเซล ยังไม่รวมงานออกแบบมือถือในแผนนี้
- ไม่เปลี่ยนหน้าตา Activity Mode, Reminder Mode หรือ Telegram bot หาก phase นั้นไม่จำเป็นต้องแตะ

## Phase 0 — ทำสัญญาพฤติกรรมให้ตรงระบบจริง

**เป้าหมาย:** ใช้ mockup เป็นแบบหน้าจอได้โดยไม่พาความสามารถจำลองที่คลาดเคลื่อนเข้าระบบจริง

1. ทำรายการ mapping ของปุ่ม การ์ด สถานะ และข้อความใน mockup กับ state/action/API ที่มีอยู่จริง แยกสิ่งที่มีแล้วกับสิ่งที่ต้องสร้าง
2. กำหนดกฎสิทธิ์ให้ตรง: โควต้าและสิทธิ์นักพัฒนาควบคุมเฉพาะงานที่เรียก AI; คำถามสำเร็จรูป การอ่านตารางแบบกำหนดกฎ และขั้นตอนสร้างร่างที่ไม่ใช้ AI ยังใช้ได้ตามสิทธิ์ของผู้ใช้
3. กำหนดป้ายแหล่งคำตอบตามผลลัพธ์จริง เช่น `AI`, `ปฏิทิน`, `ข้อมูล T.i.M.E.S.` และ `คำตอบสำเร็จรูป` ห้ามติดป้าย AI ให้ผลลัพธ์ที่ไม่ได้เรียก AI
4. ระบุพฤติกรรมที่ mockup แสดงแต่ระบบยังไม่มี เช่น ปุ่ม `หยุด` ที่ต้องยกเลิกคำขอจริง และตัวเลือกเวลาที่ mockup คำนวณจากข้อมูลจำลอง อย่านำปุ่มเหล่านี้ขึ้น production ในสภาพที่กดแล้วไม่ทำงาน

**จบ phase เมื่อ:** มีตาราง mapping สั้น ๆ และรายการงานค้างที่ตรวจได้; ไม่มีข้อความหรือสถานะในแบบที่จะทำให้ผู้ใช้เข้าใจผิดเรื่องสิทธิ์ การบันทึก หรือแหล่งข้อมูล

## Phase 1 — ย้ายโครงหน้า PC

**เป้าหมาย:** เปลี่ยน AI Mode ให้เป็นหน้าแชทหลักกับแผงงานด้านขวา โดยยังใช้ conversation hook และ backend เดิม

1. แยกส่วนแสดงผลออกจาก `activity-assistant-dialog.jsx` ตามหน้าที่ เช่น ส่วนหัว, บทสนทนา, composer และ work rail โดยไม่ย้าย logic ธุรกิจเข้า JSX/CSS
2. นำสัดส่วน chat + rail จาก mockup มาใช้ใน AI Mode จริง แผงงานต้องเปิด/ปิดได้ และแชทต้องยังอ่านได้เมื่อแผงเปิด
3. ให้ช่องพิมพ์อยู่ในพื้นที่ใช้งานตลอด ส่วนบทสนทนาและแผงงานเลื่อนแยกกัน; ปุ่มกลับและเมนูหลักยังทำงานตาม navigation เดิม
4. ย้ายเฉพาะสไตล์ที่ใช้จริงมาเป็น CSS ของฟีเจอร์ ห้าม import ไฟล์ใน `src/dev/mockups` เข้าชุด production

**จบ phase เมื่อ:** สลับ Activity/Reminder/AI แล้ว state ไม่หายผิดจังหวะ, ไม่มีการเลื่อนแนวนอนบน PC, ช่องพิมพ์และปุ่มส่งไม่หลุดจอ, build ผ่าน และภาพ PC สองขนาดอ่านง่าย

## Phase 2 — บทสนทนาและการคุยอิสระ

**เป้าหมาย:** ใช้หน้าใหม่คุยได้ต่อเนื่อง โดยคงสิทธิ์ โควต้า และประวัติเดิม

1. เชื่อม `คุยอิสระ` และ `วางแผนกิจกรรม` กับ endpoint ปัจจุบัน แสดงข้อความผู้ใช้ คำตอบ ที่มา และสถานะกำลังรอ/ล้มเหลวตามผลจริง
2. รักษาประวัติแชทที่แยกตามบัญชีและการสลับไปโหมดอื่น; ปุ่ม `แชท AI ใหม่` ล้างเฉพาะบทสนทนา AI บนเว็บ
3. แสดงโควต้า สิทธิ์นักพัฒนา และทางเลือกเมื่อใช้ AI ไม่ได้ โดยไม่ปิดเครื่องมือที่ไม่ใช้ AI
4. ทำคีย์บอร์ด `Enter` ส่งและ `Shift + Enter` ขึ้นบรรทัดใหม่เฉพาะเมื่อทดสอบแล้วว่าไม่รบกวนการพิมพ์ภาษาไทย/IME

**จบ phase เมื่อ:** ส่งข้อความทั่วไป รับคำตอบ สลับโหมด กลับมาอ่านประวัติ และแก้ข้อผิดพลาดด้วยการลองใหม่ได้; ไม่มีข้อความซ้ำหรือหักโควต้าซ้ำจากการกดส่งซ้อน

## Phase 3 — เครื่องมืออ่านข้อมูลและการ์ดผลลัพธ์

**เป้าหมาย:** แผงงานเรียกเครื่องมือจริงและผลลัพธ์อยู่ในบทสนทนา

1. เชื่อมคำถามสำเร็จรูป, ดูตาราง, สรุปวันนี้ และหาเวลาว่างกับบริการเดิม โดยแสดงขอบเขตวันและที่มาของข้อมูลให้ชัด
2. แสดงการ์ดตาราง ช่วงเวลาว่าง ไม่พบข้อมูล และข้อผิดพลาดใกล้ข้อความที่เรียกเครื่องมือนั้น; ตัวเลือกที่กดแล้วต้องอัปเดตผลลัพธ์จริง
3. รักษาการอ่าน Calendar แบบจำกัดช่วงและสิทธิ์เดิม อย่าส่งข้อมูลกิจกรรมทั้งบัญชีไปให้โมเดลหรือแสดงข้อมูลที่ backend ไม่ได้คืนมา

**จบ phase เมื่อ:** เครื่องมือทั้งสี่ใช้ข้อมูลจริง, กรณีตารางว่าง/ข้อมูลไม่พร้อม/สิทธิ์ Calendar หมดอายุมีทางไปต่อ, ป้าย AI ตรงกับการเรียก AI จริง

## Phase 4 — สร้างกิจกรรมและตรวจร่าง

**เป้าหมาย:** ทำเส้นทาง `คุย → เลือกเวลา → ร่าง → ตรวจ → ยืนยัน` ให้ครบในหน้าใหม่

1. เชื่อมขั้นตอนถามข้อมูลกับ conversation state เดิม แสดง stepper ในแผงงานเฉพาะขณะสร้างกิจกรรม
2. แสดงร่างในแชทและข้อมูลแก้ไขในแผงงาน โดยแก้ชื่อ วัน เวลา และระยะเวลาแล้วผลทั้งสองตำแหน่งตรงกัน
3. ใช้ validation, กฎเวลาชน และช่วงเวลาแนะนำจากระบบจริง ไม่ใช้ `findSlots` หรือข้อมูลวันแบบ hard-code ของ mockup
4. ส่งร่างที่ผ่านการตรวจไปยังขั้นตอนบันทึกเดิม ให้ผู้ใช้กดยืนยันครั้งสุดท้ายก่อนเขียน Calendar; รองรับยกเลิกและกลับมาแก้

**จบ phase เมื่อ:** ทดสอบสร้างหนึ่งกิจกรรม, แก้ร่าง, เวลาเต็ม/เวลาชน, ยกเลิก, และบันทึกสำเร็จหรือผิดพลาด โดยไม่มีการสร้างรายการจากคำตอบ AI เพียงอย่างเดียว

## Phase 5 — Telegram และความทนทานของหน้า

**เป้าหมาย:** ข้อมูลประกอบไม่รบกวนแชทหลัก และการเปลี่ยนหน้าหรือบัญชีไม่ทำให้ state ผิดคน

1. ย้ายสำเนา Telegram ไปไว้ในส่วนพับของแผงงาน แสดงจำนวนข้อความและข้อผิดพลาดตามข้อมูลจริง แยกการล้างสำเนา Telegram จากการเริ่มแชท AI ใหม่
2. ตรวจการสลับบัญชี การออกจากระบบ คำขอที่ตอบกลับช้า การกดซ้ำ และการกลับมาจาก Activity/Reminder
3. เพิ่มการยกเลิกคำขอจริงก่อนเปิดใช้ปุ่ม `หยุด`; หากยังไม่พัฒนา ให้ไม่แสดงปุ่มนี้ในหน้า production

**จบ phase เมื่อ:** ข้อมูลไม่ข้ามบัญชี, ไม่มีคำตอบเก่ามาเติมแชทใหม่, Telegram ไม่ปะปนกับข้อความ AI, และทุกปุ่มที่เห็นทำงานตรงชื่อ

## Phase 6 — เพิ่มความสามารถ AI หลังหน้าใหม่มั่นคง

**เป้าหมาย:** ให้ AI ช่วยงานได้มากขึ้นด้วยข้อมูลที่ตรวจสอบได้ โดยใช้ backend ร่วมกับ Telegram เมื่อเหมาะสม

**สถานะ 27 ต.ค. 2026:** เส้นทางอากาศบน PC เชื่อม Google Weather ผ่าน backend แล้ว ใช้เกณฑ์เลือกช่วงร่วมกับ Telegram แสดงแหล่งข้อมูลและเวลาอัปเดต เลือกช่วงเพื่อเปิดร่างใน ActivityModal และมีปุ่มถามต่อวันถัดไป/วันเดิมโดยส่งบริบทเดิมตรง ๆ การบันทึกต้องให้ผู้ใช้ยืนยันใน modal เสมอ ผ่านการทดสอบด้วยข้อมูลจำลอง; ยังต้องลองกับ Google Weather และ Calendar ของบัญชีจริงก่อนถือว่าจบ phase

1. เลือก use case แรกหนึ่งอย่างที่วัดผลได้ เช่น `ถามอากาศ → เลือกช่วงที่เหมาะ → ร่างกิจกรรมเพื่อตรวจ` หรือ `อ่านข่าว → พบวันสำคัญ → ร่างกิจกรรมเพื่อตรวจ`
2. แยกบริการข้อมูลข่าว/อากาศออกจากส่วนแสดงผล Telegram แล้วเปิดเป็นเครื่องมือ backend ที่เว็บเรียกได้ตามสิทธิ์เดียวกัน ไม่คัดลอก logic หรือเปิด API key ใน frontend
3. ส่งให้ AI เฉพาะข้อมูลที่เครื่องมือคืนมา พร้อมสถานที่ เวลาอัปเดต แหล่งข้อมูล และข้อจำกัดของข้อมูล; ทดสอบคำถามต่อเนื่องอย่าง `พรุ่งนี้ล่ะ` หรือ `ที่เดิม` โดยไม่ให้โมเดลเดา context ที่ไม่มี
4. ประเมินคำตอบกับกรณีข้อมูลขาด, API ล้มเหลว, วันที่คลุมเครือ และข้อมูลเปลี่ยนก่อนเปิดใช้จริง

**จบ phase เมื่อ:** use case แรกทำได้ครบตั้งแต่ถามจนได้ร่างที่ตรวจได้ ผู้ใช้เห็นว่า AI ใช้ข้อมูลใด และไม่มีการแต่งข่าว/อากาศ/วันนัดหมายที่แหล่งข้อมูลไม่ได้ให้มา

## กติกาตรวจรับทุก phase

- ตรวจเฉพาะความเสี่ยงของงานใน phase นั้นด้วย unit/integration test และ browser test ที่เกี่ยวข้อง; รัน frontend build ก่อนส่งมอบ
- ตรวจภาพบน PC ขนาดที่กำหนดและลองกดเส้นทางหลักจริงก่อนถือว่า phase เสร็จ
- สรุปสิ่งที่ทำ สิ่งที่ยังจำลองหรือยังไม่รองรับ และผลทดสอบทุกครั้ง
- ยังไม่ push หรือ deploy จนกว่าจะได้รับคำสั่งจากเจ้าของโปรเจกต์

**ลำดับเริ่มงาน:** ทำ Phase 0 แล้ว Phase 1 ก่อน จากนั้น Phase 2–5 ตามลำดับ เมื่อหน้าและข้อมูลจริงนิ่งแล้วจึงเริ่ม Phase 6 โดยเลือก use case แรกเพียงเรื่องเดียว
